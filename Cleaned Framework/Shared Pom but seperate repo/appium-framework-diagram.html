How it flows, end to end

  1. Test layer — test scripts use Page Objects and test data, driving actions through the Appium client library.
  2. Client library — converts calls into W3C WebDriver / JSON Wire Protocol HTTP requests.
  3. Appium server — manages the session from your desired capabilities and routes commands to the right driver.
  4. Drivers — UiAutomator2/Espresso for Android, XCUITest for iOS, translate commands into native automation calls.
  5. Target device — a per-platform agent (UiAutomator2 Server via ADB on Android, WebDriverAgent via Xcode on iOS) executes gestures and assertions against the app under test.
  6. CI / reporting — GitHub Actions, GitLab CI, Jenkins, or Azure DevOps kick off runs; grids and device clouds scale them; Allure produces reports.

Why it's laid out this way

  1. everything under src/test — this is a test-automation project with no shippable application code, so framework/support code (drivers, config, pages, utils, data) and the actual tests all live under src/test; there is no src/main.
  2. ThreadLocal driver — DriverManager binds one driver per thread, enabling safe parallel execution across devices.
  3. Page Object Model — locators and screen actions live in pages/, so a UI change touches one file, not every test.
  4. BaseTest — centralises setup/teardown so every test class inherits driver lifecycle handling.
  5. Listeners — auto-screenshots on failure and retry-on-flaky, with no changes to test code.
  6. Externalised resources — capabilities, test data and app binaries sit in resources/, so you switch platform/environment without recompiling.
  7. Reference catalogues — pages/examples/ documents every locator strategy and UI interaction in code (see docs/LOCATORS_AND_INTERACTIONS.md), so new contributors have a worked example of each.
  8. Environment profiles & quality gates — config.<env>.properties overlays switch environments via -Denvironment=; Spotless + .editorconfig and a pre-commit hook keep formatting and builds consistent (see docs/ADVANCED_FEATURES.md).
  9. Shared parent POM — dependency/plugin versions are inherited from automation-parent, so this framework and the Playwright one stay in lock-step and never drift.
