How it flows, end to end

  1. Test layer — a JUnit 5 test extends BaseTest; @BeforeEach asks the driver layer for a fresh page.
  2. Driver layer — PlaywrightFactory reads config, picks the browser engine, launches it, and stores Playwright/Browser/Context/Page in PlaywrightManager ThreadLocals.
  3. Config layer — ConfigReader supplies base URL, browser, and timeouts; -D overrides win over the file.
  4. Page objects — the test calls intent-revealing methods on page objects, which drive auto-waiting Playwright locators.
  5. Browser → app — Chromium / Firefox / WebKit executes actions against the app at base.url.
  6. API layer (no browser) — API tests (@Tag("api")) extend BaseApiTest; ApiRequestFactory builds an APIRequestContext, service clients like UserService call endpoints, and JsonUtils parses responses against api.base.url.
  7. Reporting / CI — @Steps, failure screenshots, trace, and optional video (opt-in via -Drecord.video=true, off by default) feed Allure; GitHub Actions, GitLab CI, Jenkins, or Azure DevOps install browsers, run tests, and publish the report. API tests run browser-free on any agent.

Why it's laid out this way

  1. everything under src/test — this is a test-automation project with no shippable application code, so framework/support code (config, driver, pages, utils, data) and the tests all live under src/test; there is no src/main.
  2. ThreadLocal driver — PlaywrightManager gives each thread its own browser stack, enabling safe parallel runs.
  3. Page Object Model — locators and actions live in pages/, so UI changes touch one file.
  4. BaseTest + extension — centralises page lifecycle and auto-attaches failure screenshots without touching test code.
  5. Externalised config — browser, URL and timeouts come from config.properties with -D overrides, so no recompiling to switch.
  6. Auto-waiting locators — Playwright removes most explicit waits and flakiness compared with classic Selenium waits.
  7. UI and API share one toolchain — API tests use Playwright's APIRequestContext (no browser), reusing the same JUnit 5, Allure, config and ThreadLocal model; service clients in api/ mirror page objects.
  8. Resilience & quality tooling — @Retry for flaky tests, AuthState storageState reuse, network mocking, config.<env>.properties overlays, plus Spotless + .editorconfig and a pre-commit hook (see docs/ADVANCED_FEATURES.md).
  9. Shared parent POM — dependency/plugin versions are inherited from automation-parent, so this framework and the Appium one stay in lock-step and never drift.
